# Rumics

Rumics — минималистичный приватный чат с комнатами и шифрованием сообщений на стороне клиента.

Проект сейчас находится на стадии MVP. Главная идея — сервер хранит только зашифрованные сообщения и зашифрованный ключ комнаты, а пароль и расшифровка остаются в браузере пользователя.

## Возможности MVP

- создание комнаты с ограниченным временем жизни;
- настройка комнаты при создании: удаление после N часов бездействия и лимит сообщений (0 — выключено);
- подключение по ID или ссылке комнаты;
- защита комнаты паролем;
- получение соли и зашифрованного ключа комнаты через API;
- генерация ключа комнаты в браузере;
- шифрование сообщений через Web Crypto API и AES-GCM;
- хранение в PostgreSQL только ciphertext и IV;
- чат-интерфейс: время отправки у каждого сообщения, свои сообщения справа, чужие слева;
- различение своих и чужих сообщений внутри шифрованного payload — сервер остаётся zero-knowledge;
- атомарный счётчик сообщений в БД: при исчерпании лимита отправка отклоняется с `403`;
- автоматическое удаление истёкших комнат и комнат без активности;
- каскадное удаление сообщений вместе с комнатой;
- получение новых сообщений через polling.

Сервер не получает пароль и plaintext сообщений. Однако текущая версия ещё не является полноценной production-системой: нет WebSocket, аккаунтов, сложной авторизации и защиты от злоупотребления известным ID комнаты.

## Архитектура

```text
Browser A ── encrypt ──> Go API ──> PostgreSQL
Browser B ── polling ───> Go API ──> PostgreSQL
Browser B <── decrypt ─── ciphertext + IV
```

Ключ комнаты создаётся в браузере. При создании он шифруется ключом, производным от пароля и соли, после чего на сервер отправляется только зашифрованная версия. Для сообщений используется ключ комнаты.

Сообщения шифруются как JSON-объект `{ "v": 1, "uid": "...", "text": "..." }`, где `uid` — случайный идентификатор вкладки. По нему после расшифровки фронт отличает свои сообщения от чужих; сервер видит только ciphertext и IV. Сообщения старого формата (голый текст без JSON) отображаются как чужие.

## Миграции базы данных

Схема базы описана миграциями в каталоге `migrations/` (SQL-файлы формата golang-migrate) и применяется утилитой `migrations/migrate.go`. Задай `DATABASE_URL` и запусти утилиту из корня проекта:

PowerShell:

```powershell
$env:DATABASE_URL = "postgres://username:password@localhost:5432/rumics_db"
go run ./migrations
```

Bash (Linux/macOS):

```bash
export DATABASE_URL="postgres://username:password@localhost:5432/rumics_db"
go run ./migrations
```

Утилита применяет все неприменённые миграции (`*.up.sql`). Если схема уже актуальна, команда завершается без изменений.

Нюанс: драйвер мигратора по умолчанию требует SSL. Если PostgreSQL работает без SSL, добавь `?sslmode=disable` в `DATABASE_URL` (сервер на pgx этот параметр тоже принимает).

## Запуск

Не добавляй пароль PostgreSQL прямо в исходный код. Сервер читает строку подключения из переменной окружения `DATABASE_URL`.

PowerShell:

```powershell
$env:DATABASE_URL = "postgres://username:password@localhost:5432/rumics_db"
go run .
```

После запуска открой:

```text
http://localhost:8080
```

Для проверки компиляции:

```powershell
go test ./...
```

## Бэкапы и восстановление

`scripts/backup.sh` делает дамп PostgreSQL через `pg_dump -Fc` в `scripts/dumps/`, пишет лог в `scripts/logs/backup.log` и удаляет дампы старше семи дней. `DATABASE_URL` скрипт берёт из окружения или из `.env` в корне проекта; требуются установленные `psql` и `pg_dump`.

`scripts/restore.sh ПУТЬ_К_ДАМПУ` восстанавливает базу из дампа. Рестор всегда выполняется вручную и только в пустую базу: если в целевой БД уже есть пользовательские таблицы, скрипт откажется работать, чтобы не затереть данные.

### Автоматический бэкап через systemd (Linux)

Юниты в `systemd/` запускают бэкап раз в сутки по таймеру; восстановление таймером не автоматизируется — только `restore.sh` вручную.

1. Скопируй юниты на сервер и поправь путь к проекту (в юните по умолчанию `/opt/rumics`):

```bash
sudo cp systemd/back-up.service systemd/back-up.timer /etc/systemd/system/
sudo sed -i 's|/opt/rumics|/путь/к/проекту|g' /etc/systemd/system/back-up.service
chmod +x scripts/backup.sh
```

2. Включи таймер:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now back-up.timer
```

3. Проверь работу:

```bash
systemctl list-timers back-up.timer        # расписание следующего запуска
sudo systemctl start back-up.service       # разовый бэкап без ожидания таймера
```

Таймер срабатывает каждый день в 03:00 по местному времени (`OnCalendar`). Если сервер был выключен в этот момент, бэкап выполнится после включения (`Persistent=true`).

## Проверка двумя пользователями

1. Открой сайт в обычном окне браузера.
2. Создай комнату и скопируй её ссылку.
3. Открой ссылку в режиме инкогнито.
4. Введи пароль и подключись.
5. Отправь сообщения из обоих окон: свои отображаются справа на фиолетовом, чужие — слева на сером, у каждого сообщения время отправки.

Вторая вкладка получает новые записи примерно раз в 1,5 секунды. Для проверки с другого устройства используй IP компьютера в локальной сети вместо `localhost` и открой порт `8080` в firewall.

После полной перезагрузки страницы ключ комнаты исчезает из памяти браузера. Это ожидаемое поведение текущей zero-knowledge-схемы: нужно снова подключиться по паролю. После переподключения сообщения, отправленные до перезагрузки, отображаются как чужие — идентификатор вкладки генерируется заново.

## API

- `POST /create` — создаёт комнату и возвращает ID и соль. Параметры: `expire` (часы жизни, обязателен), `idle_expire` (часы без активности до удаления, пусто/0 — выключено), `max_messages` (лимит сообщений, пусто/0 — без лимита);
- `POST /api` — сохраняет зашифрованный ключ комнаты;
- `POST /connect` — возвращает соль, зашифрованный ключ комнаты и IV;
- `POST /messages` — сохраняет ciphertext и IV сообщения; инкрементирует счётчик комнаты, при исчерпании лимита или истёкшей комнате возвращает `403`;
- `GET /messages?room_id=...&after_id=...` — возвращает новые сообщения (id, ciphertext, IV, время создания).

## Roadmap

Планируемые изменения:

1. Заменить polling на WebSocket-архитектуру для доставки сообщений в реальном времени.
2. Добавить обработку небольших файлов, включая изображения, видео и аудио, с отображением файлов внутри чата.
3. Исследовать поддержку комнат более чем на двух пользователей. Для этого потребуется понятная схема идентификации участников в интерфейсе без аккаунтов.
4. Перейти с HTTP на HTTPS и настроить TLS для безопасной передачи данных между браузером и сервером.

## Ограничения текущего MVP

- сервер не проверяет пароль комнаты напрямую;
- любой, кто знает ID комнаты, может отправлять запросы к её API;
- polling создаёт регулярную нагрузку на сервер;
- ключ комнаты хранится только в памяти страницы;
- идентификатор вкладки (`uid`) генерируется заново при каждой загрузке страницы — сообщения, отправленные до перезагрузки, отображаются как чужие;
- нет имён пользователей;
- загрузка файлов пока не реализована.
