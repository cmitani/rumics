# Rumics

Rumics — минималистичный приватный чат с комнатами и шифрованием сообщений на стороне клиента.

Проект сейчас находится на стадии MVP. Главная идея — сервер хранит только зашифрованные сообщения и зашифрованный ключ комнаты, а пароль и расшифровка остаются в браузере пользователя.

## Возможности MVP

- создание комнаты с ограниченным временем жизни;
- настройка комнаты при создании: удаление после N часов бездействия и лимит сообщений (0 — выключено);
- подключение по ID или ссылке комнаты;
- защита комнаты паролем;
- получение соли и зашифрованного ключа комнаты через API;
- генерация ключа комнаты в браузере;
- шифрование сообщений через Web Crypto API и AES-GCM;
- хранение в PostgreSQL только ciphertext и IV;
- комнаты на нескольких участников: ники (свой или `userN` по порядку входа), лимит участников и статус «не в сети»;
- отправка файлов до 10 MB: шифруются ключом комнаты на клиенте, тело передаётся сырым потоком (`application/octet-stream`, без base64-кодирования), скачивание ленивое — по кнопке;
- чат-интерфейс: время отправки у каждого сообщения, свои сообщения справа, чужие слева;
- различение своих и чужих сообщений внутри шифрованного payload — сервер остаётся zero-knowledge;
- атомарный счётчик сообщений в БД: при исчерпании лимита отправка отклоняется с `403`;
- сессионные cookie: доступ к сообщениям только после доказательства владения ключом комнаты (SHA-256 отпечаток ключа), чужой запрос с известным ID комнаты получает `401`;
- Argon2id с 64 MiB памяти для вывода ключа шифрования из пароля.
- автоматическое удаление истёкших комнат и комнат без активности;
- каскадное удаление сообщений вместе с комнатой;
- получение новых сообщений через WebSocket-push; при обрыве соединения фронт автоматически переподключается и на это время возвращается к HTTP-polling.

Сервер не получает пароль и plaintext сообщений. Однако текущая версия ещё не является полноценной production-системой: нет WebSocket, аккаунтов, сложной авторизации и защиты от злоупотребления известным ID комнаты.

## Архитектура

```text
Browser A ── encrypt ──> Go API ──> PostgreSQL
Browser B ── polling ───> Go API ──> PostgreSQL
Browser B <── decrypt ─── ciphertext + IV
```

Ключ комнаты создаётся в браузере. При создании он шифруется ключом, производным от пароля и соли, после чего на сервер отправляется только зашифрованная версия. Для сообщений используется ключ комнаты.

Сообщения шифруются как JSON-объект `{ "v": 1, "uid": "...", "text": "..." }`, где `uid` — постоянный идентификатор браузера (генерируется один раз и хранится в `localStorage`). По нему после расшифровки фронт отличает свои сообщения от чужих и находит ник автора; сервер видит только ciphertext и IV. Для таблицы участников сервер хранит только отпечаток `SHA-256(uid)` — как и с ключом комнаты, проверка без знания значения. Сообщения старого формата (голый текст без JSON) отображаются как чужие.

Доступ к сообщениям выдаётся по сессии. При создании комнаты браузер отправляет на сервер отпечаток ключа `SHA-256(roomKey)` — это хэш, сам ключ сервер не видит. После подключения (или создания) браузер доказывает владение ключом через `POST /auth` и получает HttpOnly-cookie `rumics_session` на 12 часов, привязанную к комнате. `GET/POST /messages` без валидной сессии для этой комнаты возвращают `401`. Cookie получает флаг `Secure` автоматически, когда запрос пришёл через HTTPS (напрямую или за reverse proxy с `X-Forwarded-Proto`).

## Миграции базы данных

Схема базы описана миграциями в каталоге `migrations/` (SQL-файлы формата golang-migrate) и применяется утилитой `migrations/migrate.go`. Задай `DATABASE_URL` и запусти утилиту из корня проекта:

PowerShell:

```powershell
$env:DATABASE_URL = "postgres://username:password@localhost:5432/rumics_db"
go run ./migrations
```

Bash (Linux/macOS):

```bash
export DATABASE_URL="postgres://username:password@localhost:5432/rumics_db"
go run ./migrations
```

Утилита применяет все неприменённые миграции (`*.up.sql`). Если схема уже актуальна, команда завершается без изменений.

Нюанс: драйвер мигратора по умолчанию требует SSL. Если PostgreSQL работает без SSL, добавь `?sslmode=disable` в `DATABASE_URL` (сервер на pgx этот параметр тоже принимает).

## Запуск

Не добавляй пароль PostgreSQL прямо в исходный код. Сервер читает строку подключения из переменной окружения `DATABASE_URL`.

PowerShell:

```powershell
$env:DATABASE_URL = "postgres://username:password@localhost:5432/rumics_db"
go run .
```

После запуска открой:

```text
http://localhost:8080
```

```powershell
go test ./...
```

E2E-тесты гоняются против живого сервера (нужны PostgreSQL с применёнными миграциями и запущенный `go run .`):

```bash
pip install -r tests/requirements.txt
```

Покрывают: выдачу сессии по отпечатку ключа и `401` без неё, лимит сообщений, WebSocket (отказ без cookie, пуш сообщений, presence-кадры), слоты участников с воскрешением по `uid_hash` и полный цикл файлов. ## Бэкапы и восстановление

`scripts/backup.sh` делает дамп PostgreSQL через `pg_dump -Fc` в `scripts/dumps/`, пишет лог в `scripts/logs/backup.log` и удаляет дампы старше семи дней. `DATABASE_URL` скрипт берёт из окружения или из `.env` в корне проекта; требуются установленные `psql` и `pg_dump`.

`scripts/restore.sh ПУТЬ_К_ДАМПУ` восстанавливает базу из дампа. Рестор всегда выполняется вручную и только в пустую базу: если в целевой БД уже есть пользовательские таблицы, скрипт откажется работать, чтобы не затереть данные.

### Автоматический бэкап через systemd (Linux)

Юниты в `systemd/` запускают бэкап раз в сутки по таймеру; восстановление таймером не автоматизируется — только `restore.sh` вручную.

1. Скопируй юниты на сервер и поправь путь к проекту (в юните по умолчанию `/opt/rumics`):

```bash
sudo cp systemd/back-up.service systemd/back-up.timer /etc/systemd/system/
sudo sed -i 's|/opt/rumics|/путь/к/проекту|g' /etc/systemd/system/back-up.service
chmod +x scripts/backup.sh
```

2. Включи таймер:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now back-up.timer
```

3. Проверь работу:

```bash
systemctl list-timers back-up.timer        # расписание следующего запуска
sudo systemctl start back-up.service       # разовый бэкап без ожидания таймера
```

Таймер срабатывает каждый день в 03:00 по местному времени (`OnCalendar`). Если сервер был выключен в этот момент, бэкап выполнится после включения (`Persistent=true`).

## Проверка двумя пользователями

1. Открой сайт в обычном окне браузера.
2. Создай комнату и скопируй её ссылку.
3. Открой ссылку в режиме инкогнито.
4. Введи пароль и подключись.
5. Отправь сообщения из обоих окон: свои отображаются справа на фиолетовом, чужие — слева на сером, у каждого сообщения время отправки.

Вторая вкладка получает новые записи примерно раз в 1,5 секунды. Для проверки с другого устройства используй IP компьютера в локальной сети вместо `localhost` и открой порт `8080` в firewall.

После полной перезагрузки страницы ключ комнаты исчезает из памяти браузера. Это ожидаемое поведение текущей zero-knowledge-схемы: нужно снова подключиться по паролю. После переподключения сообщения, отправленные до перезагрузки, отображаются как чужие — идентификатор вкладки генерируется заново.

## API

- `POST /create` — создаёт комнату и возвращает ID и соль. Параметры: `expire` (часы жизни, обязателен), `idle_expire` (часы без активности до удаления, пусто/0 — выключено), `max_messages` (лимит сообщений, пусто/0 — без лимита);
- `POST /api` — сохраняет зашифрованный ключ комнаты и отпечаток ключа (`key_hash`, base64 SHA-256), по которому позже проверяется сессия;
- `POST /connect` — возвращает соль, зашифрованный ключ комнаты, IV и настройки комнаты (`settings`, включая `max_users`); если лимит участников исчерпан — `403`;
- `POST /auth` — принимает `room_id` и `key_hash`; при совпадении с отпечатком выдаёт HttpOnly-cookie сессии на 12 часов;
- `POST /join` — вход в комнату участником: `room_id`, `uid_hash` (base64 SHA-256 от uid), опциональный `nick`. Новый участник занимает слот (при заполненной комнате — `403`), существующий «воскрешается» (сброс `dead`, обновление `last_seen`) с сохранением ника. Клиент повторяет `/join` раз в минуту как heartbeat; участники без активности 10 минут помечаются `dead` и освобождают слот;
- `POST /messages` — сохраняет ciphertext и IV сообщения; требует сессию (`401` без неё), инкрементирует счётчик комнаты, при исчерпании лимита или истёкшей комнате возвращает `403`;
- `GET /messages?room_id=...&after_id=...` — возвращает новые сообщения (id, ciphertext, IV, время создания); требует сессию (`401` без неё);
- `GET /ws?room_id=...` — WebSocket-upgrade для комнаты; требует сессию (`401` без cookie). Сервер пингует соединение каждые 30 секунд и пушит кадры `{"type": "message", "id", "ciphertext", "iv", "created_at"}`, `{"type": "file", "id", "header", "header_iv", "iv", "created_at"}` и `{"type": "presence", "members": [...]}`. Отправка сообщений остаётся через `POST /messages` (гибридная схема, как у Discord/Slack);
- `POST /files?room_id=...&iv=...&hiv=...&header=...` — загрузка файла: тело запроса — сырой ciphertext (`application/octet-stream`, лимит 10 MB), в query-параметрах IV тела и маленький зашифрованный header с именем/типом/размером и автором;
- `GET /files?room_id=...&after_id=...` — метаданные файлов комнаты для истории (ciphertext не входит);
- `GET /file?id=...` — отдаёт тело одного файла сырым потоком `application/octet-stream`; требует сессию комнаты.

## Roadmap

Планируемые изменения:

1. Перенести отправку сообщений в WebSocket, когда появятся события от клиента (печатает, присутствие).
2. Идентификация участников между устройствами (сейчас uid живёт в localStorage одного браузера).
3. Превью изображений и чанковая загрузка больших файлов.

## Прод-развёртывание

Прод-инстанс работает за Caddy: TLS-сертификаты и rate limiting (`/create`, `/connect`, `/messages`) настроены на стороне proxy, Go-сервер слушает HTTP на localhost. Пример конфигурации — `Caddyfile` в корне репозитория (директива `rate_limit` требует сборку Caddy с плагином `mholt/caddy-ratelimit`). Cookie сессии получает флаг `Secure` автоматически благодаря `X-Forwarded-Proto` от Caddy. Сессии хранятся в памяти сервера, поэтому после его рестарта клиентам нужно переподключиться к комнате (ввести пароль заново).

## Ограничения текущего MVP

- сервер не проверяет пароль комнаты напрямую;
- `POST /connect` остаётся открытым и отдаёт соль и зашифрованный ключ комнаты по известному ID — защита от офлайн-подбора пароля это Argon2id (64 MiB) и rate limit на proxy;
- комнаты, созданные до появления `key_hash`, не смогут пройти `/auth` и получить доступ к сообщениям — дождись их истечения или пересоздай;
- при живом WebSocket polling не используется, но остаётся резервным каналом при обрыве соединения;
- ключ комнаты хранится только в памяти страницы;
- сессии живут в памяти сервера и живут 12 часов — после рестарта сервера или истечения нужно переподключиться;
- идентификатор (`uid`) хранится в `localStorage` одного браузера: очистка данных сайта или смена устройства делает участника «новым» (новый номер/ник), а старые сообщения теряют привязку к нику;
- участники помечаются «не в сети» по heartbeat-таймауту 10 минут, а не по факту закрытия вкладки — статус может запаздывать;
- нет имён пользователей;
- лимит файла 10 MB, файлы без чанков и докачки;
- превью изображений в чате пока не реализовано.
